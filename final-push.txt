===============================================================================
1. NON-NEGOTIABLE END STATE
===============================================================================

1. Rocky Linux remains the host operating system and Linux remains the control
   plane. The Linux kernel core is not being rewritten in Rust.
2. The host runs a version-pinned, Rocky-derived custom kernel package with
   CONFIG_RUST enabled and the toolchain required by that exact kernel source.
3. Only the three project-owned host kernel modules needed by the hybrid are
   conversion targets:

   - ihk.ko
   - ihk-smp-x86_64.ko
   - mcctrl.ko

4. Each production module is a native Rust-for-Linux module with its own Rust
   module entry point, Kconfig option, Kbuild rule, signed .ko, symbol namespace,
   dependency declaration, lifecycle, and evidence manifest.
5. A production module may call ordinary Linux kernel functions implemented in
   C through kernel-provided Rust abstractions or a narrowly audited Rust FFI
   abstraction. That does not make the project module a C implementation.
6. No production module may compile, link, load, or dispatch into a
   project-authored C implementation body, compatibility helper, fallback,
   companion shim, archive, or prebuilt C object.
7. Public C UAPI headers may remain because unchanged C applications consume
   them. Generated bindings, generated Kbuild module metadata, linker scripts,
   kernel headers, and Linux-core objects are allowed boundaries.
8. Required x86 instructions may use Rust asm! or global_asm!. Any remaining
   standalone project assembly must be separately justified, hashed, reviewed,
   and allowlisted. Assembly is never counted as Rust source merely because it
   is embedded in a Rust file.
9. ihk-smp-x86_64.ko may depend on ihk.ko. mcctrl.ko may depend on the IHK
   interfaces. Standalone means each is a distinct native Rust module without a
   project C implementation dependency; it does not mean dependency-free.
10. The C reference modules remain available only as test oracles in a clearly
    separated reference build. They are forbidden from production packages,
    initramfs contents, installed module trees, and the production link graph.
11. The existing McKernel image, mcexec, ihklib, ihkconfig, ihkosctl, ihkmond,
    mcstat, other host tools, Rocky user space, and Linux core are not new Rust
    conversion targets. They remain compatibility consumers and test oracles.
12. The existing Rust-first McKernel image is preserved and regression-tested;
    this tracker does not require further conversion of its remaining C or
    assembly primitives.
13. x86_64 is the production architecture in this tracker. Arm64, MIC, and Tofu
    do not earn, consume, or dilute these 10,000 evidence points.
14. Rocky kABI support is not claimed. Kernel packages and all three modules are
    built, signed, installed, upgraded, and rolled back as one exact-version set.

The clean one-sentence architecture is:

  A Rocky-derived Linux control plane with native Rust-for-Linux IHK, SMP, and
  mcctrl host modules controls the existing McKernel co-kernel over a versioned
  UAPI and IKC boundary.

3. SCORING CONTRACT
===============================================================================

The denominator is permanently 10,000 evidence points. One basis point equals
0.01 percentage point. Only PASS earns points.

Permitted status values:

  TODO          no accepted evidence and no active claim
  IN_PROGRESS   work or evidence generation is active; earns zero
  BLOCKED       a named prerequisite or defect prevents acceptance; earns zero
  PASS          all acceptance criteria passed on named immutable evidence

There is no partial credit. A gate that is 99 percent internally complete still
earns zero until its complete acceptance contract passes. If work needs useful
incremental credit, it must be split in advance into independent, measurable,
weighted child gates without changing the 10,000-point denominator.

Every PASS record must identify immutable evidence. At minimum that evidence
must bind:

  - full source commit and dirty-tree state;
  - exact Rocky source RPM or kernel source commit;
  - kernel NVR, build ID, configuration digest, and compiler/tool digests;
  - ihk.ko, ihk-smp-x86_64.ko, mcctrl.ko, and McKernel image digests;
  - test and benchmark manifest digest;
  - hardware, firmware, topology, NUMA, governor, IRQ placement, and mitigations;
  - exact commands, parameters, seeds, repetitions, and injected fault IDs;
  - machine-checked assertions and raw-log manifest digest;
  - fatal-signature scan and cleanup/resource-ledger result;
  - durable run URL plus a committed compact evidence manifest.

Anti-inflation rules:

  - no points for source lines, commits, plans, wrappers, or tests merely added;
  - no points for compiling when the functional acceptance gate says runtime;
  - no points for a Rust wrapper whose behavior still executes project C;
  - no skipped, expected-failure, waiver, or best-effort credit;
  - an untriaged failure prevents PASS even if a later cherry-picked rerun passes;
  - fault tests pass only if evidence proves that the intended fault fired;
  - performance evidence includes every sample, the warmup policy, exclusions,
    confidence intervals, and environment controls;
  - a shared ABI, kernel config, toolchain, abstraction, or module-lifecycle
    change invalidates every dependent PASS until replayed;
  - the exact tested module and RPM digests must be the released digests;
  - unsupported work remains in the denominator unless this scope contract is
    explicitly revised and all weights are rebalanced to 10,000;
  - documentation-only edits do not invalidate technical evidence;
  - any source-affecting change records an impact set and marks affected gates
    TODO before a new score is published.

Update protocol:

  python3 scripts/final_push_tracker.py --check
  python3 scripts/final_push_tracker.py --update
  python3 scripts/final_push_tracker.py --check --json evidence/final-push.json

The generated top block is never edited by hand. Every green commit must pass
the tracker checker, which validates unique IDs, legal statuses, concrete PASS
evidence, exactly 10,000 points, each workstream subtotal, and the generated
summary digest. Long-running tests publish non-scoring live counters in their
evidence, while the weighted gate remains zero until its threshold passes.

5. DEPENDENCY-ORDERED IMPLEMENTATION PLAN
===============================================================================

Stage A: lock the reference and observable contract

  A1. Preserve f2eb7352 and its exact run as the immutable legacy smoke oracle.
  A2. Build a second C-reference profile on the chosen custom Rocky kernel so
      C and Rust modules can be compared on the same Linux core and hardware.
  A3. Extract all three modules' active build inputs from Kbuild .cmd files and
      final link maps, not source-directory guesses.
  A4. Inventory exported and imported symbols with namespaces and versions.
  A5. Inventory module parameters, device nodes, ioctls, compat ioctls, mmap and
      poll behavior, sysfs and procfs paths, binfmt behavior, status values,
      IKC packets, boot parameters, structure layouts, errors, logs, and cleanup.
  A6. Assign every observable row a feature ID, Rust owner, acceptance test,
      negative test, fault test, and benchmark where applicable.

Stage B: create the Rocky-derived Rust kernel product

  B1. Start from a checksum-pinned Rocky kernel source RPM and its full patch,
      configuration, RPM macro, certificate, and source manifest.
  B2. Preserve Rocky configuration by default and apply a small reviewed delta.
  B3. Enable CONFIG_RUST and its exact prerequisites; run rustavailable in the
      same build environment used for RPM production.
  B4. Resolve CONFIG_MODVERSIONS explicitly. Either use a kernel line where Rust
      module versioning is supported or disable it and enforce exact NVR atomic
      kernel-module deployment. Do not claim Rocky kABI compatibility.
  B5. Build with the best-supported complete LLVM path unless the selected Rocky
      kernel proves an equally supported alternative.
  B6. Add only generic, reusable Rust abstractions to the kernel patch stack.
      McKernel policy and protocol logic remains inside the project modules.
  B7. Integrate the three Rust sources as native in-tree Kbuild modules in the
      custom kernel source. The McKernel repository remains the source of truth;
      a deterministic manifest stages the reviewed files into the kernel tree.
  B8. Produce one signed RPM family and preserve an official Rocky rescue entry.
  B9. Record the source, config, toolchain, build log, build ID, symbols,
      Module.symvers, BTF, signatures, RPM contents, and reproducibility result.

Stage C: define shared Rust contracts before porting behavior

  C1. Keep public C UAPI headers for unchanged applications; generate Rust
      declarations from them or generate both languages from a neutral schema.
  C2. Never bind private legacy implementation structs as the new design.
      Replace them with Rust types that encode ownership and state transitions.
  C3. Introduce newtypes for CPU IDs, NUMA IDs, OS IDs, physical addresses,
      virtual addresses, page counts, byte counts, vectors, generation IDs, and
      channel IDs. Require checked conversions at all external boundaries.
  C4. Centralize status, ioctl, IKC, boot, monitor, and error definitions.
  C5. Build safe-as-possible wrappers for the kernel APIs listed in WS20.
      Direct bindings belong only inside the abstraction layer, never scattered
      through leaf driver logic.
  C6. Attach a written invariant to every unsafe block, unsafe impl, raw pointer,
      FFI callback, shared-memory access, DMA-like mapping, and assembly block.
  C7. Implement generation-tagged registries and a resource ledger so stale IDs,
      ABA reuse, double release, and incomplete teardown are detectable.

Stage D: port ihk.ko first

  D1. Establish the module lifecycle and exported core registration contract.
  D2. Port device and ioctl surfaces while preserving UAPI and errno behavior.
  D3. Port driver and OS registries using explicit Rust ownership and reference
      rules; prohibit raw stored pointers without a documented lifetime anchor.
  D4. Port resource allocation and mapping with rollback objects whose Drop
      paths restore partially acquired resources.
  D5. Port IKC queues and master/listener lifetimes with explicit memory ordering,
      queue invariants, wrap arithmetic, capacity, and backpressure.
  D6. Differential-test every public operation before downstream modules depend
      on it. Do not begin production qualification on a C-backed fallback.

Stage E: port ihk-smp-x86_64.ko

  E1. Consume only the versioned ihk Rust interface and ordinary Linux APIs.
  E2. Model CPU and memory ownership as explicit state machines so partial
      reserve, boot failure, stop, reset, and release cannot double-own state.
  E3. Preserve Linux CPU hotplug and IRQ affinity state and restore exact values.
  E4. Validate every physical range and arithmetic operation before mapping or
      copying the McKernel image.
  E5. Port the x86 boot sequence with explicit register, stack, CR3, APIC, IPI,
      trampoline-address, cache, barrier, and timeout contracts.
  E6. Keep unavoidable assembly tiny and mechanically comparable to the legacy
      sequence; prefer asm or global_asm within the Rust crate.
  E7. Prove Intel and AMD behavior separately; neither substitutes for the other.

Stage F: port mcctrl.ko

  F1. Consume the native IHK module interfaces and preserve unchanged mcexec and
      ihklib behavior.
  F2. Anchor every persistent IKC listener, callback, process, request, VMA,
      work item, and wait object in module-lifetime or reference-counted storage.
  F3. Port ioctl and process lifecycle before the broad syscall surface.
  F4. Port syscall families in observable, independently tested slices. Each
      slice must cover success, errno, interruption, restart, cancellation,
      invalid pointers, process exit, concurrency, and cleanup.
  F5. Port futex and ptrace only with dedicated race, timeout, exit, and lock
      testing; compile success is not meaningful evidence for these paths.
  F6. Port procfs, sysfs, and binfmt with explicit unregister and in-flight-use
      barriers so module exit cannot race an active callback.
  F7. Remove every C object and helper only after equivalent Rust runtime evidence
      exists, then run the link-map and source-closure audits.

Stage G: integrate and qualify the exact production artifacts

  G1. Run the same C and Rust module matrices on the same custom kernel, hardware,
      firmware, topology, governor, IRQ policy, McKernel image, and workloads.
  G2. Require exact functional and data parity. Performance is compared with
      distributions and confidence bounds, not single best-case samples.
  G3. Run fast deterministic gates before expensive stress; never use a soak to
      replace a missing unit, ABI, fault, or differential test.
  G4. Every long run continuously checks data, state, resources, warnings,
      watchdogs, progress counters, and host health so a silent hang cannot pass.
  G5. Release the exact RPM and module digests that passed production gates.

7. ZERO-PROJECT-C CLOSURE
===============================================================================

The final closure is object- and behavior-based, not extension-based.

Required checks for each .ko and the RPM closure:

  1. Parse Kbuild .cmd files and the complete compiler invocation log.
  2. Enumerate every object, archive member, linker script, and generated input.
  3. Fail if GCC or Clang compiles any project .c file for a production module.
  4. Fail if a Rust object imports a project C helper or fallback symbol.
  5. Fail if any reachable archive contains a project C implementation.
  6. Inspect ELF, BTF, DWARF language tags, relocations, undefined symbols,
     exported symbols, module metadata, and build IDs with readelf, nm, objdump,
     pahole, bpftool, modinfo, and the kernel's modpost output.
  7. Compare undefined imports to an explicit allowlist of ordinary Linux kernel
     exports and versioned native Rust inter-module exports.
  8. Verify the build context physically excludes legacy project C sources.
  9. Inspect RPM file lists, initramfs, installed module trees, weak-updates,
     depmod output, and loaded module paths for accidental legacy copies.
  10. Boot and run with the C reference packages unavailable.

Allowed non-Rust inputs:

  - unchanged Rocky and upstream Linux kernel core objects;
  - generated Rust bindings and generated Kbuild module metadata;
  - public C header declarations consumed by bindgen or unchanged user space;
  - linker scripts and build metadata;
  - an explicit, minimal, hashed x86 assembly allowlist when Rust asm cannot
    express the required relocation or entry contract.

Forbidden inputs:

  - project .c implementation bodies;
  - project C wrappers for inline functions or macros used as convenience;
  - C fallback branches selected by configuration or runtime dispatch;
  - prebuilt C objects or static archives;
  - function pointers that route a Rust surface back into a project C body;
  - reference modules installed beside production modules under another name.

8. BENCHMARK METHODOLOGY AND ACCEPTANCE LIMITS
===============================================================================

Reference configurations:

  R0  Frozen f2eb7352 Rocky 8.10 smoke oracle for regression continuity.
  R1  Legacy C modules rebuilt for the selected custom Rocky kernel. This is the
      preferred functional and performance A B oracle.
  R2  Native Rust modules on the exact same custom Rocky kernel and hardware.
  R3  Official Rocky kernel on the same hardware for host-kernel regression
      checks that do not require McKernel modules.

An R1 versus R2 comparison changes only the module set. All other variables are
identical: kernel NVR, firmware, microcode, mitigations, BIOS configuration,
governor, turbo policy, C-states, topology, isolated CPUs, IRQ affinity, NUMA
placement, memory, McKernel image, user space, filesystems, workloads, seeds,
warmup, repetitions, collection tools, and ambient-service policy.

Statistical rules:

  - record raw samples, monotonic timestamps, warmup samples, failures, retries,
    interruptions, and environment changes;
  - predeclare sample size from the percentile and confidence target;
  - use paired randomized A B order when reset cost permits;
  - report median, mean, standard deviation, MAD, p90, p95, p99, p99.9,
    p99.99 where sample count supports it, minimum, maximum, and bootstrap
    confidence intervals;
  - judge regression with the adverse confidence bound, not the point estimate;
  - never delete outliers without preserving them and applying a predeclared,
    equally applied rule with and without exclusion results;
  - detect thermal, frequency, interrupt, scheduler, NUMA, and background-load
    drift and invalidate contaminated comparisons;
  - functional mismatches always fail regardless of speed.

Default production performance limits unless a stricter feature limit exists:

  - exact output, data, errno, signal, side effect, and final-state parity;
  - throughput at least 97 percent of the valid R1 reference lower confidence
    bound;
  - median latency regression no greater than 3 percent;
  - p99 latency regression no greater than 5 percent;
  - p99.99 or maximum-jitter regression no greater than 10 percent;
  - host CPU consumption regression no greater than 5 percent at equal work;
  - retained memory after cleanup returns to the measured baseline with zero
    monotonic growth; steady-state overhead must be explained and budgeted;
  - zero dropped, duplicated, reordered, corrupted, or unacknowledged operation;
  - zero unexpected kernel taint, warning, Oops, panic, stall, hung task, lockdep,
    sanitizer, refcount, RCU, leak, or data-integrity finding.

All benchmark evidence must include the exact commands and machine-readable
result JSON. A chart or prose summary without raw sample digests cannot pass.

===============================================================================
12. RELEASE-READY DEFINITION
===============================================================================

RELEASE READY changes to YES only when all 130 weighted gates are PASS and the
generated score is exactly 100.00 percent on the exact release commit and exact
release artifact digests.

The final audit must prove all of the following together:

  - Rocky-derived kernel packages are reproducible, signed, installable,
    bootable, recoverable, and version-pinned;
  - CONFIG_RUST and required kernel infrastructure are present in the running
    production kernel;
  - ihk.ko, ihk-smp-x86_64.ko, and mcctrl.ko are distinct native Rust modules;
  - production module artifacts contain no project C implementation or fallback;
  - unchanged McKernel and user-space consumers retain declared compatibility;
  - functional, ABI, error, state, and cleanup parity pass;
  - all production benchmark, stress, fault, fuzz, sanitizer, security,
    reliability, and performance gates pass;
  - no warning, sanitizer issue, leak, mismatch, unexplained failure, or release
    blocker remains;
  - install, update, rollback, rescue, telemetry, and triage procedures pass;
  - the tested artifacts and released artifacts are byte-identical;
  - the complete evidence set is signed, durable, and independently auditable.
