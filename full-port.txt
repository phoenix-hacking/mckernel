Point Accounting
------------------------------------------------------------
- A percentage point is one percentage-point increase in a category's `Complete` value
  above. For example, one category moving from 41.0% complete to 43.0% complete
  is +2.0 aggregate campaign percentage points.
- The campaign total is the sum of verified category percentage-point deltas,
  not a count of helper functions, commits, validation cases, or slices.
- Movement should retire or demote McKernel-owned C implementation bodies from
  the default x86_64/Rocky path, or move a required default-path operation's
  validation, mutation, traversal, dispatch, lifetime, side-effect sequencing,
  or user-visible output shaping into Rust while preserving C fallback builds.
- C may remain for public ABI wrappers, external Linux/kernel/libc interfaces,
  generated/vendor code, tests, explicit fallback builds, and unavoidable
  assembly-adjacent surfaces.
- Runtime-sensitive work must not be counted as full standalone completion until
  it has direct runtime coverage.
- Each planned conversion step should aim for about +10.0 aggregate category
  percentage points of code movement before verification. If safety, ownership
  boundaries, or direct coverage make +10.0 unsafe, record the shortfall and
  verify the largest safe slice instead.
- Earlier validation-history labels that counted helper-slice units are
  superseded by this aggregate percentage-point accounting.

Completion Plan
------------------------------------------------------------
1. Finish the x86_64/Rocky standalone OS default path:
   allocator/free lifetime, lock/list/refcount/atomic primitives, page-table/TLB
   and user-copy primitives, process/thread/object lifecycle mutation,
   scheduler/context-switch/wait/futex/signal side effects, syscall dispatch,
   Linux-forwarding callbacks, and IKC/control-plane exchange.

2. Complete host/IHK/mcctrl ownership:
   module-load, OS create/destroy, memory registration, IKC send/receive,
   device lifecycle, kmsg/notifier/event paths, and mcctrl syscall/procfs/sysfs
   command bodies.

3. Complete user tools:
   mcexec, mcstat, mcinspect, eclair, crash helpers, dump helpers, ihkosctl,
   ihkconfig, ihkmond, ihklib, and smaller utilities while preserving CLI flags,
   output formats, exit codes, config parsing, ioctl/protocol behavior, and
   script compatibility.

4. Retire C fallbacks:
   keep C fallback during validation, then remove McKernel-owned C fallback
   bodies once Rust equivalence and runtime coverage prove the replacement.

5. Final gate:
   remaining C must be limited to compatibility headers/wrappers, approved
   external Linux/libc/kernel interface glue, tests, generated/vendor code, or
   unavoidable assembly-adjacent code.

Verification Requirements
------------------------------------------------------------
Every completed slice must pass the strongest relevant non-reboot gate:
- Rust formatting/static checks for touched Rust files.
- Focused equivalence or smoke coverage for the moved behavior.
- Rust-enabled builds relevant to the touched area.
- C fallback build until that fallback is intentionally retired.
- Ownership report/dashboard checks when tracker percentages move.
- Module-load smoke for IHK/mcctrl changes.
- QEMU/KVM guest validation for runtime-sensitive changes.

Runtime validation must use QEMU and virtualization tooling:
- Prefer KVM when available and verified for the run.
- Fall back to TCG only when KVM is unavailable.
- Do not run host reboot paths.
- Use guest-only McKernel boot/workload validation.
- Required runtime gates before final completion: Rocky QEMU boot smoke,
  module load/unload, OS create/destroy, minimal user workloads, focused V11
  regression, and stress coverage for memory faults, page tables, allocator
  pressure, futex/wait, signals/ptrace, XPMEM, procfs/sysfs, IKC, and shutdown.

Stop on first validation failure and record the failing command, environment,
and short error summary in kernel.log before unrelated changes.
