Concrete decisions required before selecting the whole candidates:

* mmap range: current writer unlock followed by reader reacquire permits removal or replacement; XPMEM's actual provider stores `att->at_vmr = vmr`, making an unlocked pointer or address-only relookup insufficient. The actual rwspinlock has one atomic counter and no existing downgrade function. Propose an independently reviewed lock-owner primitive that atomically changes the held write state to one reader with release semantics, keeps the existing preemption-disable count, and is paired with the existing reader unlock. Verify all XPMEM callbacks and lock order with that continuous reader guard. Alternatively provide a real range reservation integrated with all removal paths. Neither proposal is implemented or approved here; holding the writer through XPMEM may deadlock and needs lock-order review.
* mmap descriptor: `syscall_mckfd_find_locked` drops the process lock before callback and the close path detaches and frees. A functional solution needs a pin or equivalent coordinated with all close, process teardown and callbacks; holding the spinlock across an arbitrary mmap callback may recurse/sleep. No pointer copy proves lifetime.
* mmap straight phase: both `straight_va` publication and search/add operations occur before ordinary writer acquisition, and readers/removers share these fields. Review moving the whole prephase under `memory_range_lock`, including search/add/page-table provider nested locking and failure semantics, or use a process-scoped initialization protocol coordinated with all readers/removers. Do not add local serialization that excludes those participants.
* fork gettid: `syscall_settid_body_result` initializes request bytes and sends count/address. `act_gettid` allocates the full array, `mcexec_collect_active_tids_result` writes each live ID and zero-fills all remaining entries, and successful ioctl transfer precedes the response. Error returns avoid reading the pool. Bind the actual selected executor and prove synchronous whole-transfer completion before treating this as production initialization evidence; this source chain does not itself prove native operation.
* fork: preserve existing owned constructor outcomes and CPU release ownership, including the helper-thread path that selects current CPU without `obtain_clone_cpuid`. Establish scheduler/accounting disposition for that path. Ptrace callback changes state and attaches before wake; retain reservation and graph lifetime until all callbacks, report attachment, enqueue and TID snapshot complete. The snapshot routine reads range, object and path under VM reader lock and copies bounded path bytes; prove path ownership/immutability under that guard and current VM lifetime. The parent pointer in the owned fork call is read before a visible update-lock acquisition, so demonstrate the existing parent-graph contract or use the appropriate owner-reviewed snapshot/reference rather than assuming a pin.
