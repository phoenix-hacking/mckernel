During that interval the current callback-based find can increment the same count from zero under the hash reader lock. The separate `M14-PENDING-LIFETIME-INTERLEAVING-20261104-1` fixture imports both actual original bodies and models that sequence. The candidate changes only Rust `find_thread`: its private helper scans under the existing hash reader lock and uses an atomic `SeqCst` increment-if-positive, refusing negative, zero and `i32::MAX` counts. It retains the hash lock until the increment succeeds or the node is skipped. Existing owned `hold_thread`, its void callback ABI, the generic `process_find_thread_body_result`, and C fallbacks remain unchanged. A warning for an exited thread occurs only after a successful new hold; original `hold_thread` warned before increment. Rejecting exhausted/invalid counts and declining an expired match are intentional differences, and hash-list uniqueness and normal lookup fallback remain subject to independent profile review.

The experimental CMake overlay requires whole ARCH5 selection and selects the participant cfg, but does not set the reviewed exclusion flag. Offset-based aliases and all linked callers need separate coverage proof.

The selected Rust spinlock saves IRQ state, disables preemption, acquires its ticket, then unlocks, enables preemption and restores the saved state; the Rust MCS writer routes through the same operations. This is source evidence for nested save/restore, not a full lock-order, interrupt, fairness or scheduling proof. Candidate slot operations do not themselves allocate, usercopy, free or schedule while holding the bucket lock. The earlier actual-body mock fixture exercised publication conflict, copy failures and snapshot/update concurrency, but does not establish kernel ownership.

The lookup candidate has narrower scope than global Thread lifetime: direct `arch_do_kill_thread_target_result` and process-sibling signal paths use independent ordinary holds, and procfs has its own borrower/hold issue. Legacy C fork failure can force a published refcount to one; the full28 supported CLONE_VM Rust fork is separately documented as having its host-error edges before publication, so that legacy observation cannot be transferred automatically. `terminate_host_body_result` also has a force-to-one case requiring proof that the detached Thread has no publication or outstanding holds. Do not select this candidate as complete slot/lifetime closure until all applicable selectors, refcount resets, direct readers and destruction edges are independently reviewed and the full candidate is built and qualified.
