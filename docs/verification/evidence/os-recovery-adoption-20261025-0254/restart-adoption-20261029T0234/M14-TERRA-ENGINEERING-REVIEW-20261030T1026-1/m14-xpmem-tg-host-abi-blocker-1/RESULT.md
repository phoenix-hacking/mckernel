# XPMEM TG references and host close ABI

Functional McKernel OS/apps and Rust/assembly migration only; no security testing.

Status: SOURCE ONLY. No new Rust implementation, test execution, runtime outcome, native acceptance or shared edit. Extends `../m14-xpmem-open-owner-blocker-1/RESULT.md`.

In selected retained `kernel/rust/xpmem_helpers.rs` SHA256 `e8c7970b672c724f14da2eb0a12fdbcd11df62f824422a5f8a98da4364328255`, `xpmem_tg_ref_by_tgid_wrapper_result` (`:6236-6340`) locks the partition bucket for reading, calls `xpmem_tg_ref_by_tgid_nolock_body_result` (`:6190-6234`), and unlocks; the latter takes a TG reference on the matching non-destroying entry. `xpmem_tg_ref` uses the real `XpmemThreadGroupPrefix.refcnt` (`kernel/rust/abi.rs:1269-1289`, Rust ABI assertions `:2211-2218`) and `xpmem_tg_deref_bridge` delegates to the checked count/drop/free body (`xpmem_helpers.rs:2178-2189,6504-6555`). The creation body initializes the TG's not-destroyable count to one and publishes it under bucket writer lock (`:3936-3983,6610-6679`). A reference can therefore preserve TG allocation storage while held; it is not an open ownership contract and does not by itself preserve partition, hash membership, VM/thread fields, or prevent TG logical destruction.

The current `xpmem_open_tg_body_result` returns only int. On an existing TG it drops the just-acquired reference and returns success; on a new TG it returns the same success after publishing the initialized object. A private internal `Created` versus `Shared` token is ABI-feasible in isolation, but a creation tag alone does not authorize rollback of the linked TG because another caller could acquire and use it after publication. A coherent owner needs a bucket-locked create-or-acquire decision, a held per-open TG edge, last-open release/unlink/flush semantics, partition lifetime and VM/thread ownership. Clone must acquire/release the same edge and unwind on failure; those contracts are not established by the existing API. No correctness conclusion is inferred from the reference count alone.

There is an existing generic guest request pathway: `kernel/rust/syscall_policy.rs` SHA256 `11d9d9e14c6c4ee3d593083ce18137414a7780c23507a44fb0834937fa9618e4`, `syscall_generic_forwarding` at `:2611-2660` and request body at `:2927-2958` initialize a request from a syscall number and six arguments and call the selected `do_syscall`. Therefore it would be inaccurate to say that generic close forwarding cannot be expressed. The retained materialized host source `executer/user/mcexec.c` SHA256 `310301305e41bab4eda63026849ee6f166bb6e5d4d6f2c789aa8003e94745056` has a close branch at `:8651-8663`: selected `act_close` or C fallback runs close-plan/generic-syscall/overlay deletion and returns the result. Retained `executer/user/rust/mcexec_helpers.rs` SHA256 `8f9fbe474220433118e6662c9f2517f73a547730575b83ffb73255d06e9b40d7` implements `act_close` at `:1516-1527`. These are source facts, not proof of the active host binary or a new transport release.

Missing host interface: a source-bound XPMEM rollback owner needs a matched close request adapter for the exact open executor/OS identity and FD, plus completion/error semantics that distinguish a completed consumed FD from a request that did not complete or whose host disposition is uncertain. An unknown or negative close response must not be silently treated as rollback success or retried against a possibly reused FD. It also needs a policy for retaining the unpublished guest TG/partition owner when host close disposition is unresolved. Neither the XPMEM open callback set (`xpmem_helpers.rs:3371-3416`) nor the retained caller provides this adapter or error-to-owner contract. The actual transport/host selection, completion and error semantics have not been proven; no mock may supply that proof.

Next: bind the selected host close provider, requester/OS and completion semantics read-only, and independently design/review the TG/partition created-or-shared ownership and clone/close rollback under the real bucket and descriptor locks. Only after both contracts exist can an ABI-preserving internal token and actual-body candidate be built. Do not issue host requests, change held transport, or run tests without applicable admission.
