# Monitoring-slot lock and owned-fork prerequisite

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Source-only investigation, no patch, tests, compiler or physical operation. INPUT-HASHES.json binds the retained candidate and separately labels canonical kernel/process.c; actual assembled configuration and scheduler source remain unproved.

The retained C-compatible `Process` definition (abi.rs:1458-1524) has `update_lock`, `threads_lock`, `children_lock`, `mckfd_lock`, `perf_status` and a raw `monitoring_event`, but no dedicated slot lock/reference or spare documented per-process storage. Adding a field changes C/Rust ABI and offsets; a Rust static lock or side table could avoid that particular layout change but requires explicit process initialization/removal, process identity/address-reuse, global contention/IRQ policy, and all-path synchronization. Neither alternative is an existing slot ownership API. Process's own refcount protects a process according to its separate lifecycle; no source shows it pins a perf event or prevents monitoring slot replacement.

The retained scheduler candidate x86_cpu_helpers.rs:5442-5466 reads the slot with no locally acquired lock. Its caller context in canonical kernel/process.c:6816-6932 saves/disables local IRQs and holds a CPU-local runqueue spinlock through `arch_switch_context`. Thus any slot lock there must be IRQ-safe and satisfy `runq -> slot`; no sleeping, host offload or potentially blocking final cleanup may happen under it. Canonical process.c:7203-7211 already takes `runq -> process.update_lock`; however the existing perf slot writers and exit/switch readers do not all take update_lock, and no source-bound ordering proves that adding `runq -> update_lock` plus ioctl/hash, descriptor, thread, group and teardown operations is deadlock-free. `threads_lock` is held in selected Rust do-exit at syscall_policy.rs:35621-35625, whereas remote perf ioctl holds process hash reader for its target lookup; neither is a common all-reader/slot lock. `mckfd_lock` is used around VM close callbacks and does not bind monitoring readers. Reusing any one of them requires coordinated changed paths and a demonstrated order; current source does not supply it.

The owned-fork selector is an actual separate branch: retained CMakeLists.txt:51 defaults `ENABLE_NATIVE_FORK_OWNED_TRANSACTION` OFF, and retained syscall.c:8244 bypasses legacy inherited-pointer copy when ON. Retained fork_runnable_child.rs:28-36 checks parent.monitoring_event is null at `admit`, and :113-118 executes admission after submit_start; this is a bounded eligibility condition, not a monitoring reference or proof a different CPU cannot publish after the load. Do not infer release/selection of owned fork, modify its held transfer/ACK, or infer this check covers legacy selection.

First exact missing fact is a selected-source, nonblocking acquire/release provider for a live event while atomically reading the process slot, and a reviewed `runq -> slot -> event/group` (or equivalent) order compatible with remote process-hash lookup, process thread/descriptor locks, stop/exit and CPU scheduler. It must define replacement and old pin release, process teardown and inherited/fork ownership, prevent an event from being freed while a reader is between slot load and use, and defer potentially blocking finalization outside all IRQ/runqueue/slot locks. A new lock alone does not provide the event pin, and load-then-ref can race last free. Exact counter-owner and generic FD/clone handoff remain additional blockers.

A real Rust patch and actual-body regression cannot be honestly asserted safe until these provider and order contracts exist; no model-only test substitutes for them. The next executable source step is an independently reviewed, source-paired event pin and slot ownership protocol with exact IRQ/runqueue lock order and all selected writer/reader/teardown/fork bindings; only then can a private source successor be implemented and tested under a reviewed light profile.
