The source co-located with the 57546 build shows `MCEXEC_UP_GET_CREDV` dispatch to `mcctrl_exec::credentials`, which copies eight raw u32 values through `UserSlice` to a **user virtual address**. The legacy GET_CRED argument is a McKernel **physical address**: existing legacy `mcexec_getcred` calls `phys_to_virt` and writes eight u32 to that mapping. They are not interchangeable. The qualified Rust module does not resolve this operation to the legacy C `mcexec_getcred` or legacy `mcctrl_control_getcred_body_result` symbol; those names are absent from its visible symbol table. The saved extracted-body mock for the latter therefore supports that legacy source body only.

A correct physical-address GET_CRED capability is a genuine prerequisite *if this legacy refresh request and 57546-family module are used together*; an alternative proven replacement protocol could remove the need for that exact ioctl. The following actual facts are not yet established for a new provider: exact OS generation and active file/context ownership; the original 32-byte guest physical buffer and permitted range/alignment; a live mapping/pin until writes and response completion; guest writer's stack/request lifecycle and non-return/cancellation handling; guest/host memory ordering and coherent publication; exact host task credential identity; behavior on bad mapping or failed completion; and the matching module/source/ABI selected for the next real guest. `smp_memory::checked_guest_bytes` in current Rust host source validates overflow and a range within an extent owned by an OsToken, but is a private SMP helper: it is not an exported mcctrl capability, does not alone establish the caller's allocation lifetime or synchronous completion, and cannot be treated as a drop-in write provider. No mapping bypass, GET_CREDV substitution or stub is proposed.

The legacy guest credential semantics need an explicit coherent transaction before any source change can be considered production-safe:

1. The host mutation must retain its actual syscall result and know whether mutation was never issued, completed with a known result, or is uncertain. Do not infer success or retry an uncertain operation.
2. When the host change is known to have succeeded, the same host-task credential owner must obtain a complete initialized eight-value snapshot. A mechanism must keep the exact host result, task identity and snapshot bound together through one authoritative response, or retain an explicit pending owner for recovery. Source has not established such a protocol here.
3. The guest must validate the entire response, maintain buffer/request and process lifetimes, and publish the matching credential fields under a proved concurrency contract **before exposing success**. `setresuid`/`setuid` families return the original host result; setfsuid/setfsgid have their own prior-ID return convention, so a uniform errno substitution is not a valid assumed fix.
4. If the host change already succeeded but a later refresh or completion fails, do not claim rollback, silently leave stale guest state while returning success, or return a normal failure as if no host mutation occurred. Retain an explicit unresolved/reconciliation state and prevent inconsistent continuation until the exact committed host state is authoritatively resynchronized under a reviewed user-visible policy. For an unknown host outcome preserve the unknown state and owner; no automatic replay or fabricated acknowledgement.

This is a source-level contract and a description of unresolved ownership, not an approved new protocol or source release. No private Rust provider is added because the physical mapping, lifecycle and post-commit policy are not established. The credential candidate remains NO-GO.
