# Perf owner candidate: target CPU and extra-register handoff blocker

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Source only. No patch, compiler, test, Docker, native, guest, privilege, controller, cleanup or replay. INPUT-HASHES.json binds retained source; actual selector, linked providers and runtime remain unproved.

A distinct concrete blocker prevents implementing a correct single opener-thread counter owner: the actual perf open scans the opener Thread PMC map (x86_perfctr.rs:435), while `perf_ioctl_body_result` can install an event in another process's `monitoring_event` for pid > 0 (syscall_policy.rs:20500). The retained x86 `arch_switch_context` for that target process invokes `perf_start` (:5457 in x86_cpu_helpers.rs). The actual `perf_start` gets the current CPU-local thread (syscall_policy.rs:26152), and `perf_counter_set` calls the selected extra-set when needed (:19828). `ihk_mc_perfctr_set_extra` (:320 x86_perfctr.rs) chooses and writes that current thread's extra map and programs the local MSR. `f03_perf_close_v1` (:26331) instead clears the closing current thread's map. Depending on actual execution, opener, target running thread/CPU and closer may differ; the event layout has no retained owner for these distinct allocations. A source-bound policy cannot safely assume they are one thread.

Existing thread hold/release APIs are real, but a descriptor-held thread reference can cycle with final Thread -> VM -> descriptor-close (prior report). A separately allocated owner can avoid that cycle only if its exact references, creation/destruction and selected Thread/event association are explicitly integrated. The missing invariant is a source-selected handoff defining which live target thread or CPU owns the extra-register reservation, how the hardware state is quiesced and transferred during schedule/migration, and how cross-thread close/target exit identifies and releases exactly that owner without a blocking callback under IRQ/runqueue/descriptor locks. The current raw extra bitmap and event fields cannot reconstruct that identity; an opener-only reserve/commit/put primitive would not satisfy it. Group/monitor slot reference handoff and host FD unknown completion are independent prerequisites.

One additional observable source fact: `perf_start_apply_event_result` (:19930) invokes `counter_set` and ignores its result before setting the event active, even though selected `perf_counter_set_body_result` can return a negative extra-register allocation result (:19828). A candidate that turns this into a propagated error changes existing behavior and needs an explicit oracle and full group/hardware rollback semantics; this task does not change or silently ignore it.

No safe actual Rust ownership primitive is offered because its owner/CPU handoff and lock ordering are not established; a disconnected abstract ledger would not alter actual providers or demonstrate correctness. Next step is a jointly reviewed target-thread/CPU lifetime and migration contract integrated with scheduler/monitor/FD/group/exit, then source-paired reserve/commit/release implementation and actual-body tests under a separately reviewed profile.
