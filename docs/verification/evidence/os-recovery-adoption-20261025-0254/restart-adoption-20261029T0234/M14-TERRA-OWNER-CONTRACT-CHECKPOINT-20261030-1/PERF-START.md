# Perf start counter-set failure: unresolved functional oracle

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Private source trace only; no code patch, test, compiler, Docker, native, guest, privilege, controller, cleanup or replay. INPUT-HASHES.json binds the retained C/Rust candidates; canonical x86 C provider is separately identified context. Actual selected linkage and runtime behavior remain unproved.

The retained original C helper `perf_start_apply_event_body_result` (nonheld syscall.c:17503-17561) calls set_period then counter_set without checking either result, ORs the counter into the start mask and marks the event active. The actual retained Rust body `perf_start_apply_event_result` (syscall_policy.rs:19919-19998) preserves that order and ignored results. Both outer bodies process leader then siblings, call counter_start for the mask, and set process perf status; both public `perf_start` wrappers discard the body's return and have void ABI. Thus blindly returning an error would be a behavior change, not a correction of a C/Rust mismatch.

The selected provider supplies a real failing path: `perf_counter_set_body_result` (:19828) invokes extra-set if required and returns -1 on its nonzero result; selected x86 `ihk_mc_perfctr_set_extra` (x86_perfctr.rs:320) changes the event's extra-register index when the preferred index is occupied, then returns -1 if the alternative is occupied too. Therefore a failure may already change event fields. A successful extra-set updates the current thread extra map and writes the CPU-local MSR before `init_raw` is called; init_raw may return an error for an invalid counter. Earlier group members can already be marked active and have hardware configuration effects before a later member fails. The existing start helper has no captured preimage, ownership token, hardware undo or synchronized group transaction. `counter_start` and set_period results are also ignored; the selected x86 set_period currently returns zero, but that does not prove arbitrary paired providers.

The narrow failure oracle must decide externally visible ioctl/start and scheduler behavior, whether a failing group is all-or-nothing or permits partial activation, and which prior event fields, per-thread extra-map reservations, CPU-local MSR state and started counters must be restored or retained on each phase. It must define failure propagation through the void `perf_start` bridge and ioctl as well as scheduler use, and bind live event/group and target CPU ownership before any change. Returning the first negative alone can leave earlier members active/configured without starting or undoing them; simply marking the failing member inactive does not settle prior or partial effects. No safe bounded Rust correction is justified by the current contract.

Next: source-paired independent group/hardware rollback and error-delivery design, then an actual-body mocked negative/positive oracle observing index mutation, mask/state transitions and all earlier/later members. Such a fixture requires a reviewed light profile and cannot establish real PMU or native behavior alone.
