# M14 ordinary XPMEM versus indexed SHM object ownership

Functional McKernel OS/apps and Rust/assembly migration only; no security testing.

The prior synthetic shmdt fixture demonstrates a missing direct registry check under a modeled `MF_XPMEM | MF_SHMDT_OK` state; it did not establish that a normal reserved attachment can have that state. This trace supports the independent review's narrower construction result: for the ordinary XPMEM attach path, with a fresh correctly behaving allocator and no later out-of-contract mutation, the new object cannot be an already live indexed SHM object and initially has no SHMDT bit. This is not a proof covering every mutation, alias or caller in the combined profile and is not an acceptance of the reservation protocol.

Source argument:

1. The XPMEM attach adapter passes `MAP_SHARED`, `MAP_ANONYMOUS` and `VR_XPMEM` to the real attach body. That body passes `MAP_SHARED | MAP_ANONYMOUS` (plus optional `MAP_FIXED`), `VR_XPMEM` and its freshly allocated attachment pointer to the existing mmap provider. See `kernel/rust/xpmem_helpers.rs:1496` and `:7447` (and C adapter `kernel/xpmem.c:8244`).
2. FULL28 `do_mmap` has a `MAP_SHARED` branch that calls `shmobj_create`, not its indexed constructor (`syscall_policy.rs:39316`). It passes this object to `add_process_memory_range`, and only then checks that returned range's memobj has `MF_XPMEM` before registering `(vm, range)` (`:39371`, `:39467`, `:39482`). An XPMEM fixed mapping first removes any existing target mapping; it does not pass that removed object's pointer to the fresh shared-anonymous constructor. Any straight-map initialization is a separate preliminary range and passes a null memobj, not the attachment's returned mapped range.
3. The current Rust `shmobj_create` allocates a new `ShmObj`, zeroes it and initializes its memobj flags to `MF_SHM` (`kernel/rust/shmobj.rs:482`–`524`). The indexed constructor calls this fresh constructor and adds `MF_SHMDT_OK | MF_IS_REMOVABLE` only to its own returned object (`:525`–`536`). The shmget path then assigns an index and inserts that indexed object into the SHM list; shmat looks up the indexed object and passes it to add-range using its own ordinary shared-memory protection flags. These paths do not pass the indexed object into the ordinary XPMEM attach `do_mmap` call.
4. Selected `process_add_range_mark_xpmem_bridge` ORs `MF_XPMEM` into the existing memobj; it does **not** clear SHMDT or check object provenance. Thus an indexed object passed into a range-marking route would retain both flags. `mremap_relocate` can retain a memobj reference and pass its existing range flags to add-range, so aliasing and lifetime must be reasoned from the real range and caller invariants; this is not a universal distinct-object proof. The local host fixture demonstrates both the normal initial flag result and that counterfactual property, but does not prove either real caller graph.

Bounds and lifetime: mmap's registration takes a VM reference and stores a stack-owned token with exact VM/range pointers, then drops the writer for synchronous XPMEM update. The pointer token and VM ref alone do not pin the range, memobj or attachment; they rely on complete mutator, detach and teardown coverage, which remains incomplete. Even if SHMDT is absent at registration, a conclusion about shmdt for the entire token lifetime additionally requires proving no permitted alias writes SHMDT to that same live memobj, and no range replacement/ABA changes the object examined by shmdt. The selected marker's raw OR is not an enforcement of these requirements. Existing `shmobj_create_indexed` creates its own object; the complete supported-profile alias/call graph and actual compiler inputs still need review. No existing live image or kernel code is changed.

The owner-specific proof is useful to classify the previous fixture: it is an adversarial unit-domain case, not a demonstrated ordinary XPMEM/shmdt race. No blanket SHMDT exclusion, guessed allocator assumption, or speculative wait is added. Next safe step: source-bind the full selected add-range caller graph and object ref/flag mutations, including mremap/clone and attachment detach; if they preserve this constructor-origin distinction, write a profile-bound invariant and source/real-layout regression before selecting any exclusion. Otherwise repair the actual owner/lifetime protocol. Independent concurrency review remains required.
