Functional McKernel OS/apps and Rust/assembly migration only; no security testing.

`do_mmap.reservation.PROPOSED.rs.inc` is an OFF private orchestration using the fault-width-corrected whole candidate. It reserves the exact linked XPMEM range while the existing VM writer lock still establishes its identity, captures diagnostic bounds, drops the writer, delegates to a lock-aware reserved XPMEM provider, prints the original error event, and releases the reservation. Non-XPMEM paths retain the original writer release and reader phase without dereferencing an unpinned pointer. Population and return use the previously copied scalars. No concrete reservation provider is claimed, no runtime selector is enabled, and there is no invented error or ACK. All other descriptor, straight-map and existing provider holds remain.

Minimum provider contract for Root/shared owners:

1. `f03_mmap_range_reserve_write_v1(vm, range)` runs under that VM's exclusive range writer, identifies this particular live range and acquires a guaranteed non-null token with both VM/range lifetime and mutation exclusion; no hidden allocation failure is assumed. Actual storage and capacity must be designed (for example range-owned state initialized with the allocation, not a bounded silently saturating table). Holding references to attachment/AP/TG alone is insufficient. Its lock/state ABI, exact teardown owner, preemption and memory ordering require review.
2. Every range mutation, removal, split, join, free, VM teardown and XPMEM detach path participates. A conflicting writer cannot wait while holding the VM writer or another lock required by the token holder: release lock, wait/retry with valid VM ownership, relookup and revalidate the object, and avoid ABA. Cover actual process helpers `split_process_memory_range`, `join_process_memory_range`, `remove_process_memory_range`, `free_process_memory_ranges`, mprotect and XPMEM detach/clear paths, including all alternative tree-mutating providers. Match lifecycle and error behavior; a list of names is not proof of complete coverage.
3. `f03_mmap_xpmem_update_reserved_v1` owns actual XPMEM update semantics with the token, not the existing update called after reader unlock. It must acquire the current VM reader before tree lookup/field accesses, release it before a same-VM stack-growth path can acquire the writer, retain the token while unlocked, reacquire/revalidate afterward, and correctly handle changes to other ranges. The existing `xpmem_pin_page_body_result` calls `page_fault_process_vm` in the missing-stack case; its stack path can take a VM writer. Ensure remote VM locks, attachment locks, page faults, scheduling, preemption, page tables and retry/error paths are reviewed for lock order and progress. Same-reserved-range recursion must be resolved by real provider invariants or an owned reentrant transition; no guessed success or deadlock avoidance policy.
4. `f03_mmap_range_release_v1` drops the token exactly once after the update and error log; no range is accessed afterwards. The provider must describe cancellation, task exit and nonreturning/error ownership, including retained state on uncertain outcomes. An atomic writer-to-reader downgrade alone does not satisfy this contract.

This proposal is a design and caller implementation, not an implementation of the three external provider operations or of all tree-writer participation. Missing work is technical and isolated to the shared provider contract; it is neither native acceptance nor a service-hold clearance.
