Bounded selected-source trace, no tests or native execution. Existing source hashes are in README.md. No changes to held direct-TID/termination or exec transfer work.

The retained pool helper stores `new` in `proc.tids[i].thread` under the process threads writer lock before `chain_thread`. In searched kernel and x86 architecture sources, concrete slot readers are `process_tid_index_for_thread_result` (process_helpers.rs:8592) and the release/replacement helpers (10992, 11039, 11799, 11940). They compare an already-supplied thread pointer, optionally clear/change the matched slot, and do not derive a new Thread reference from the stored pointer. The pool allocator checks occupancy and logs the pointer. `find_thread` instead takes a reference after lookup in the thread hash (10392 onward); chain_thread populates that hash later. This rules out acquisition from a TID slot for those examined consumers. It does not prove exclusive ownership across every callback, other representation/provider, unpublished child failure edge, or the complete process lifecycle; no actual acquired extra reference was observed.

Parent VM across setup: the parent is the current thread when the whole fork body starts, and the shared-VM constructor copies that thread's VM and process pointers without acquiring a VM edge. Snapshot_routine acquires/releases that VM's range reader before constructor. Affinity snapshot/inherit (`sched_helpers.rs:1394-1441`) holds only the affinity lock around cpuset operations, and `cpu_set` (`process_helpers.rs:9891`) holds the address-space cpuset lock for the mutation. The execution-state/remote-argument helper (`syscall_policy.rs:23901-24023`) uses parent/child fields and tracked allocation/copy; it provides no VM reference, VM identity lock or retained-owner handle. The whole fork body's original safety comment requires a live running parent; it does not establish that the copied VM allocation remains live through all intervening calls and teardown. Thus the temporary pin cannot be proven safe simply because the same raw VM pointer remains in the private candidate. No claim is made that affinity or remote setup directly replaces a VM.

Checked-hold alternative: existing `ChildCredits::acquire_with_private_cpu` (fork_child_credits.rs:105-145) checks an active current parent and CAS-pins its Thread but explicitly rejects a shared process or VM; it cannot be reused as the shared-VM abort owner. `hold_process_vm` performs an unguarded direct atomic increment through a void wrapper (process_helpers.rs:5823-5833, 9960-9985). A real checked shared-VM owner would need an actual live-parent/VM identity and lifetime contract across acquisition, a positive/non-maximum compare-exchange on that exact live VM, and a persistent disposition carrying the VM/child/CPU and already-published slot obligations on refusal or uncertainty. On successful pre-chain abort, the VM edge must be transferred exactly once to the actual final thread release. On successful chain publication, its distinct VM edge and the caller's pin must each have a separately proven owner, including partial-publication status. The standard successful VM release callback is available, but the missing admission, failure carrier, and forced child-refcount ownership prevent treating that callback alone as an implementation.

No source correction is promoted. Existing private abort-only candidate remains conditional; legacy force-reset and void chain publication are separate unresolved obligations.
