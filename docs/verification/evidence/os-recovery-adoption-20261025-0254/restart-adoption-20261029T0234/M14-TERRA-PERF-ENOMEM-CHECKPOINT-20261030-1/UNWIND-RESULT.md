# Perf standalone ENOMEM: host FD and counter ownership

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Source-only trace. No code patch, test, compiler, process operation, Docker, native, guest, privilege, controller, cleanup or replay. INPUT-HASHES.json binds retained candidate and separately retained host source; host binary selection, live identity and runtime outcomes are not proven. Earlier local-event-only candidate remains unselected and independently reviewable.

The selected perf entry calls `perf_event_open_linux_fd_body_result` (retained syscall_policy.rs:21149). Its callback is `perf_event_open_do_syscall_bridge`, which forwards request and CPU directly to existing `do_syscall` (syscall_perf_open_forward.rs). The retained C `do_syscall` binds the current requester thread, sends the request, may wait/schedule and receives `res.ret` after reply (nonheld syscall.c:4140-4442); the Rust wait body also services nested requests/backlog and can schedule. A nonnegative return is carried as `fd`; the helper then ORs the counter bit into the current entry thread's PMC map and returns, followed by mckfd allocation. On allocation NULL the entry returns -ENOMEM without closing that FD or clearing that bit (f03_perf_group_cleanup.rs).

Retained host mcexec.c:6225 and :8540 implements perf open by opening `/dev/null`, then returning the numeric FD over `do_syscall_return`; retained Rust host helper has the same bridge call. Ordinary close dispatch exists: mcexec.c:8651 or Rust `act_close` calls close-plan, generic syscall when permitted, `overlay_delfd`, then returns through `do_syscall_return`; close-plan forbids the mcctrl control FD. The guest generic request helper (syscall_policy.rs:2927) can express arbitrary number/arguments, but this perf failure branch has no source-bound close callback, no saved ownership token, and no operation-specific completion classification. In the retained host response producer, `do_syscall_return` invokes ioctl and only logs if it fails; host close can have occurred while delivery fails. A numeric result or inferred same process therefore cannot establish that the rollback request completed, was handled by the same executor/FD table/OS generation, or that an FD cannot be closed or reused by another operation. Exact host source is historical, not proof of selected binary. Issuing or retrying a close without a proof of exclusive FD identity and completed disposition risks affecting a different descriptor; unknown effects must remain owned and not be counted as rollback.

The counter is independently blocked: actual x86 `ihk_mc_perfctr_alloc` (x86_perfctr.rs:435) only scans the opener thread map and returns a free index; it does not reserve it atomically. Map OR occurs only after the host round trip. There is no transaction identity or lock proving exclusive ownership of that bit across overlapping/nested work. A blind AND-clear on failure can clear a bit acquired by another operation; it would also require a guaranteed live opener thread and source-bound access/serialization across cancellation, migration and exit. `perf_close_body_result` clears the *current closing thread* maps, not a stored opener owner, and may additionally alter an extra-register map. It is not an ownership-safe rollback callback. No demonstrated exclusive reservation, thread pin, atomic reserve/commit/release or host-FD+counter failure ledger exists.

First required interface is a source-bound operation owner that pairs the successful open response with the exact executor/OS/FD-table identity and a single-shot close request whose completion class distinguishes not-started, completed-and-consumed, and unknown; unknown stays retained and is not retried as if known. In parallel it needs a live stable counter-owner and serialized unique reservation acquired before offload, with explicit transfer, exactly-once release and exit rules. The existing generic request ABI by itself does not supply those guarantees. There is therefore no safe host-FD/counter rollback successor to implement on the available contracts. This conclusion does not invalidate the separate narrow local-event-free proposal, nor establish its acceptance. No grouped, monitoring, descriptor or other perf holds are cleared.
