# Independent pidfd compatibility review

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Source-only review; NO operation or root/native release. No syscall fixture, fork, workload or test was run. Effective configuration was unrestricted danger-full-access and approval never. Existing source and other writers were preserved.

## Findings requiring correction

1. `pidfd-compat-expert-1/deferred_fork.py:94–110`: the child calls `_restore(True)` before returning from `fork_and_pin`. Both `root_bootstrap.py:145–158` and `operation_watchdog.py:59–69` establish their child-only `try/finally: os._exit(127)` only after that call returns. If child restoration raises, including when unmasking invokes a restored raising handler, `fork_and_pin` re-raises through parent-oriented caller code in the child, with inherited descriptors still open. This is inherited from `fork-handoff-expert-1` rather than introduced by pidfd substitution. The bounded correction is a child-local nonreturning failure path around restoration (e.g. catch `BaseException` and `os._exit(127)` before any parent unwind), with the parent still retaining its own UNKNOWN custody and identity. Prove with injected child-branch source-level mocks that restore failures cannot enter parent flow; do not count a mock as real fork evidence. Parent watchdog/lease and physical retirement requirements remain separate.

2. `pidfd_compat.py:65–73` deliberately conveys an already-open descriptor in `PidfdVerificationError.fd`. `deferred_fork.py:101–105` pins it and `union_server_guarded.py:44–47` stores it. But `adapter.py:162,225–227,274–279` does not assign the descriptor when the exception occurs, and its cleanup only closes an assigned `self.pidfd`; the error carries the FD but the code does not establish durable custody after the exception is discarded. The self fixture has the same acquisition-before-`try` issue (`test_pidfd_self.py:10–19`). Correct each consumer's explicit error-FD disposition: the validator must retain/transfer it through its real failure-custody owner, or close it only if its separately reviewed semantics permit; the isolated self test may close its own error FD and fail. Do not claim the open-error path has completed a successful check.

## What the source supports

The Linux x86_64/64-bit fallback uses `ctypes.CDLL(None, use_errno=True).syscall`, fixed `c_long` syscall number and explicitly typed variadic arguments. `pidfd_open` 434 and `pidfd_send_signal` 424 match both locally read x86 UAPI headers: `/usr/include/x86_64-linux-gnu/asm/unistd_64.h` SHA256 `698d4666c969b0b4d0bed328b4a4f3cab765ec1a9948e0f14751f0ce56d91535`, and `/usr/src/linux-headers-5.15.0-139-generic/arch/x86/include/generated/uapi/asm/unistd_64.h` SHA256 `c7517b327a3d37a8ff6fea9476fc7a691e2dc124730797f45f257ddc07a46882`. Failure `-1` is mapped from captured errno, including ENOSYS/EPERM. `send_signal` has no numeric-PID signal fallback. Portable wait-status decoding accepts only exited/signalled statuses and does not establish descendant retirement. These observations are not a runtime syscall result.

Configured stop signals are deferred around the fork-to-PID/pidfd/birth handoff, using non-raising handlers plus the forking thread's signal mask. This is bounded by the code's stated assumptions: main thread, all campaign forks routed through this guard, separately retained watchdog, and no arbitrary injected exceptions or uncatchable signals. External loss of the owner and uncertain physical descendants still require independent custody and retirement; neither feature detection nor direct wait establishes that proof.

`runtime_binding.py` checks root-controlled no-symlink ancestry, immutable root-owned regular executable, exact hash and current `/proc/self/exe` identity. It also requires the exact spelling `sys.executable == path`; `/usr/bin/python3` and `/usr/bin/python3.8` are not interchangeable as configuration strings merely because they resolve to the same inode. `/usr/bin/python3.8` was read-only observed uid 0, gid 0, mode 755, one link, with SHA256 `298a9e830ed52f36c299427565485d717d1ce0179c0597cc16560513eb780b06`. Its immutable status was not inspected and no root-owned runtime or manifest is admitted here. The checkpoint's Python 3.8 feature inspection and syntax check are retained producer claims, not independent execution by this reviewer.

## Proposed separate self check and next gate

The exact `test_pidfd_self.py` obtains only `os.getpid()`, reads `/proc/self/fdinfo/<own fd>`, checks CLOEXEC/nonblocking mode, uses `pidfd_send_signal(fd, 0)` and closes the FD after a successful open. Its source creates no child and addresses no other PID; signal 0 is a real self-targeted kernel permission/existence check and must not be described as already performed. The FD error path above needs correction. A separately admitted ordinary-user profile must bind exact reviewed interpreter, fixture and compatibility bytes and their imports, CPU 6 affinity, 512 MiB memory, 30 CPU seconds, 45 wall seconds, fresh exclusive output/capture, direct-process retirement, and actual current controls/resource ownership. A zero exit plus captured output and successful close is required; errors or uncertain retirement remain failures/UNKNOWN. This focused local check provides no root supervisor, workload, mount, native or cleanup release.
