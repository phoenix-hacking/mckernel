Lock order and remaining predicates

The atomic downgrade is a concrete range-reclamation fix, not complete XPMEM lifecycle closure. xpmem_update_process_page_table_body_result stores att.at_vmr (kernel/rust/xpmem_helpers.rs:5633), so an unlocked pointer/address relookup is inadequate. The current reader prevents range writer removal/free/stack mutation, but cannot serialize teardown that itself uses a reader.

XPMEM same-VM pin lookup can call page_fault_process_vm for a missing stack range (xpmem_helpers.rs:3155 onwards). That path can acquire the same VM writer to extend stack (process_helpers.rs:2512), causing self-deadlock under the proposed retained reader. Setting is_memory_range_lock_taken to lie about a writer would permit mutation under readers and is expressly not supplied. A proper solution needs an owner-reviewed transaction: e.g. pre-fault the relevant source stack under real source writer ownership before entering the destination range transaction, pin the attachment/source graph, revalidate under destination lock, and coordinate teardown. The required retry/error semantics and cross-VM order are not guessed here.

Remote XPMEM update takes destination reader then remote source reader; concurrent remote writer callbacks and attachment lock order need review. xpmem_detach_att_body_result takes att.at_lock writer THEN VM reader (xpmem_helpers.rs:4825), clears range.private_data and invokes munmap under that reader. Ordinary detach takes VM writer THEN attachment writer (4681). remove_process_memory_range takes attachment writer under its caller's range lock (5132). Therefore adding an attachment lock around update under destination reader would introduce an actual inversion with detach_att, and does not solve this contract. This packet does not insert that unsafe local lock.

Descriptor callback pinning is independently owned by m14_generic. This candidate still imports the prior descriptor dispatch; do not select it as lifetime-qualified until the compositor binds the descriptor owner's exact interface and matching close/teardown paths.

Fork still requires selected executor whole-TID transfer binding; earlier TID-slot publication/lifetime and its reset-based legacy failure cleanup; ptrace graph/state protocol; immutable memobj.path under routine-snapshot reader; and helper CPU reservation accounting. In the helper branch, current CPU is selected without obtain_clone_cpuid, while ordinary runq_add and failure release decrement reservations. Existing sched helpers visibly decrement runq_reserved; this packet does not invent an ownership credit to suppress that debt. Normal owned non-CLONE_VM transaction already obtains a parent Thread storage ref and constructor graph credits; reuse them unchanged.
