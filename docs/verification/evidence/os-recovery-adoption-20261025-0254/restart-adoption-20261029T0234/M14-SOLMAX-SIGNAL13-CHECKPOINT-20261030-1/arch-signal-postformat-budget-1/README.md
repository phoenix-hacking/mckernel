# Private signal diagnostic post-formatter budget correction

Functional McKernel OS/apps and Rust/assembly migration only; no security testing.

`POSTFORMAT.PRIVATE.patch` changes only the private ARCH5 policy and its diagnostic-budget helper. Both input hashes match the retained ARCH5 candidate and the latest private generic/arch compositor. At both the handler and default diagnostic sites, the new sequence is **atomic signed-count check, formatter, atomic post-formatter increment**. The PID observation still occurs at every original `do_signal` entry, including nonlogging entries. The final increment acts on the then-current packed state and preserves its PID bits, so a synchronous callback that changes PID or logs recursively affects the counter before the outer update. Neither site holds a lock or carries an atomic-state reference across the formatter.

This deliberately removes the earlier reservation-before-format behavior. With initial count 63, a nested logging callback may cause two prints and leave count 65; if a callback changes PID, an outer completed print increments the new epoch. There is no global 64-message cap, no per-PID lifetime quota and no claim of ordered output. In serial and synchronous reentrant schedules where the original initialized C `int` counter and its increment remain defined, the intended check/formatter/post-increment order follows the C body. This is a source-level reasoning claim pending the proposed tests and independent review; it is not a runtime pass.

The packed PID/count remains a relaxed `AtomicU64`. Each check, PID reset and post-formatter update is atomic; it publishes no other state. The update's CAS loop retains the PID field from the state it successfully updates, including when a reset occurs before the CAS. Original unsynchronized C accesses in genuinely concurrent data-race executions have no defined parity claim. The low 32-bit update uses wrapping arithmetic without carrying into the PID: once the original signed C counter would overflow, its behavior is outside the defined C equivalence domain. The synthetic low-word-wrap source case checks field isolation only and does not claim C signed-overflow equivalence.

The exported `arch_do_signal_core_terminate_result` still takes `*const AtomicU64`, and both retained Rust callers still pass the same static atomic object. Its pointed-to object must stay live and properly aligned across both checks and after formatter callbacks. Actual object alignment, all linked consumers and exact pointer ABI remain independent blockers; this patch does not enable the whole `do_signal` selector, bind a default provider, clear ownership requirements, or prove native behavior. The 94 existing Rust `line!`/`file!`/`column!` sites remain at exactly the same coordinates. No source/debug identity was weakened.

`postformat_cases.rs` contains five deterministic source cases. It uses the actual new helper, the byte-exact pre-test prefix extracted from the previous preclaim helper, and a small independent sequential/reentrant C-order model. Cases cover nested formatting at 63, PID switch plus nested logging, a nonlogging PID switch during formatting, serial limit/reset behavior, and a synthetic low-word wrap that cannot carry into the PID. These cases do not execute real `kprintf`, the whole signal body, concurrency or kernel code. They were **not run**, and earlier preclaim-test results do not qualify this changed helper.

After independent source/ABI review and an applicable finite ordinary unprivileged resource share, the next cheap check is to compile and execute `postformat_cases.rs` once with the selected reviewed Rust test toolchain, preserve the exact command/exit/stdout/stderr and process joins, and separately inspect the two real call sites and final selected atomic storage/callers. A source-only example command shape is `rustc --edition=2021 --test postformat_cases.rs -o <fresh-output>/postformat_cases`; the output path/profile and actual execution remain the coordinator's responsibility. Failure evidence must be preserved. No compiler, test, runner, controller, guest or native action was performed for this packet, and no M14 acceptance is implied.
