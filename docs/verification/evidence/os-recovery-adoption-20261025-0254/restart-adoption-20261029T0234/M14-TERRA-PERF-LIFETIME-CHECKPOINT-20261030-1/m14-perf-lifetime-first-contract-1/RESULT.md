# M14 perf lifetime: first integration contract

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Source-only analysis; no tests, compiler, processes, physical operations or canonical edits. Actual retained candidate sources and exact hashes are in INPUT-HASHES.json. No repair is claimed.

First blocker: the actual generic descriptor lookup returns an unpinned mckfd pointer after releasing process mckfd_lock (retained syscall_policy.rs:3496); the read and ioctl paths dereference that pointer after unlock (3530, 3556). Concurrent close removes that same descriptor under the lock and calls its close callback and frees the descriptor after unlock (3625). A perf-only refcount inside the close callback cannot pin an already freed descriptor, and a group-only lock cannot protect those generic users. The existing Mckfd ABI has neither a reference count nor a lifetime callback (abi.rs:1620; process.h:415), and its layout is asserted by the candidate. The required first contract is a source-bound acquisition under the same descriptor lock, retained across every callback, with close detaching new lookup and final descriptor destruction deferred until all acquired references have retired. It must specify all descriptor consumers, clone/dup/drain and teardown, allocation/free provider and lock ordering; this generic cross-subsystem ABI/provider contract is not available in the supplied candidate. Treat it as unresolved, not as proof that any external consumer has a compatible pin.

The perf group helper separately traverses the process FD list and writes leader/list/count without that lock (syscall_policy.rs:21036), and the retained entry calls it before host syscall and FD publication (f03_perf_group_cleanup.rs). The existing actual close uses the current closing thread's counter maps and tracked free without group unlink (syscall_policy.rs:26331). FullMcPerfEvent contains raw leader/list links but no pin or closing state (35779). Consequently member-first close can leave a stale list entry, leader-first close can leave stale leader links, and concurrent group open or a callback can race reclamation. These are conditional source-level defects, not evidence of observed native execution.

A plausible successor after the first contract needs (1) FD references acquired under the descriptor lock, including a leader reference for in-flight grouped open; (2) event and leader/group lifetime references, intrusive unlink and one last-owner reclamation under a specified group lock; (3) reserve counter and private transaction state before offload, drop spinlocks during host syscall, then atomically publish descriptor/group or undo all known prepublication effects; (4) preserve host-FD ownership and rollback failure/unknown state rather than assert closure; and (5) pin the actual owning thread or move maps to an agreed stable owner with serialized allocation/release, including task exit. Leader-first semantics and interactions with read/ioctl/start/stop/child synchronization require explicit reviewed decisions and ABI/layout/source-selection bindings. This is a design sketch, not an implementation contract or C-parity oracle.

No bounded safe Rust patch can be integrated with existing interfaces alone: changing only perf close/open leaves the concrete descriptor lookup/free race. No grouped-open refusal or oracle weakening is proposed. A cross-owner descriptor lifetime change and its independent review are prerequisites before implementing the paired transactional perf group successor. Then test actual bodies for member close followed by append, leader-first close and last free, concurrent read/close/open with deterministic pins, cross-thread map owner/exit, host and descriptor allocation failures, and rollback; use an applicable reviewed execution profile. Existing standalone host-failure work is limited to the fresh unpublished self-leader and stays separate.
