# mckfd lifetime provider: source-only first contract

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. No source patch or execution, tests, compiler, Docker, native, guest, privilege, controller or cleanup. Exact sources and hashes are bound in INPUT-HASHES.json. The retained f06 Rust candidate is the selected source investigated; the current canonical process.c/xpmem.c are additional context and their identity with a future assembled build is unproven.

The descriptor layout (retained abi.rs:1620, canonical process.h:415) has next, fd, sig_no, data, opt and six callbacks; no refcount or retirement state exists. The `padding` field in Rust is actual C sig_no, not free space; `data`, `opt` and callbacks belong to distinct providers. The tracked allocation/free bridges (retained syscall_policy.rs:31588 and :31610, canonical process.c:268) directly allocate and free; they provide no pin or deferred-free interface. A sidecar could in principle retain the ABI, but no existing source-bound association, initialization, teardown, locking, allocator-failure or pointer-reuse contract covers all descriptors. Reusing provider-owned fields or assuming a global registry is already safe would invent an interface.

Retained syscall_policy.rs:3496 releases the process lock before returning the found pointer; read, ioctl, fcntl and mmap invoke callbacks after unlock (:3530-3722). Close detaches under that lock and invokes close then frees after unlock (:3625-3686). The perf group helper additionally traverses the list without a pin (:21036). Retained x86_cpu_helpers.rs:3663 traverses under lock but reads descriptor signal data after unlock in its interrupt path. A perf-only deferred event free still leaves the descriptor and other providers exposed; holding an IRQ spinlock across arbitrary callbacks/host syscall is not a valid substitute. Whether an independently established outer serialization exists in every actual selected route is unproven.

Clone specifics matter: retained process_helpers.rs:13910 locks the new process's `mckfd_lock` and copies each source descriptor by bytes from `org.proc.mckfd`; it pushes that copy then calls an optional dup callback. This source alone does not establish parent-list quiescence or parent lock ownership. The optional dup result is ignored. `process_mckfd_copy_body_result` (:7721) performs raw copy, so a refcount embedded in copied bytes would not represent a shared owner; sidecars need per-copy registration and a shared payload rule. The canonical C clone uses the same destination-lock pattern (process.c:1486). The XPMEM dup callback is provider-specific: canonical xpmem.c:7298 clears data and increments XPMEM partition `n_opened`; it is not an mckfd reference. The retained perf publication helper (syscall_policy.rs:21220) writes callback fields through fcntl but does not itself initialize `dup_cb` or `opt`; actual allocator initialization and clone use must be verified before asserting either field's value.

For teardown, retained process_helpers.rs:11537 and :11729 call each descriptor close callback while holding the process lock. The later drain (:10745) unlinks and calls the provider's free under that lock; failed clone drain also frees copied descriptors (:14028), without proving any generic callback pin retirement. A new sidecar protocol must distinguish close callback effects, callback in flight, copied/shared payload references and final descriptor free; it must avoid waiting or reentrant lock acquisition under the spinlock. Process lifetime, interrupt completion and parent/child lock ordering must be bound as well. This evidence does not prove actual full candidate source selection or all providers/consumers.

First missing contract: in the selected assembled source, identify and synchronize every raw list traversal/clone and descriptor allocation/publication/free route, including IRQ and teardown, and provide an atomic under-lock acquisition that keeps both descriptor and provider payload live until callback return. Specify whether clone may overlap parent close, how duplicate payload ownership is acquired and rolled back on failed clone, and whether close/teardown may run before all prior pins retire. Existing ABI and providers do not supply this contract. An ABI-preserving Rust sidecar is a possible design only after that contract and registration/allocator semantics are reviewed; it is not safe to implement from current evidence. Perf leader/group pins, transactional offload and cross-thread counter owner remain downstream. No grouped behavior is disabled or weakened.
