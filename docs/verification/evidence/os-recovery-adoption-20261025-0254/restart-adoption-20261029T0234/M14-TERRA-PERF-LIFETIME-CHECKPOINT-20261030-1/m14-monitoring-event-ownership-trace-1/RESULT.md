# Monitoring event publication and scheduler ownership

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. Source-only trace, no source changes, compilation, tests or physical operations. INPUT-HASHES.json binds the retained candidate files; canonical process.c and cpu.c are separately identified context and are not assumed to be the assembled source. Selection/compile/link is not proved here.

In retained syscall_policy.rs:26580-26617, `f03_perf_ioctl_v1` reads the event out of the descriptor, gets the current process, constructs the actual MCS lock node and calls `perf_ioctl_body_result` with actual process-find/unlock bridges. In :20484-20522, pid==0 ENABLE writes the current process `monitoring_event` directly then calls start; pid>0 looks up the target under process-hash reader lock, writes only when the slot is null, sets status, and unlocks the lookup. Its actual `f03_process_cleanup_find/unlock` comments and calls (:25961) bind this lock to process-hash lookup, not to event lifetime. Neither branch acquires an event/slot reference. Current-process enable may overwrite a previous pointer, so a future slot-owner protocol needs a defined replacement release.

Retained x86_cpu_helpers.rs:5442-5467 uses next.proc, tests its monitoring pointer and reloads it for reset and/or start, without acquiring a shared slot/event lock locally. Its own safety contract explicitly requires caller-provided monitoring lifetime. Canonical kernel/process.c:6816-6922 disables local interrupts, prepares the per-CPU runqueue and holds its runq lock through arch_switch_context; this establishes a concrete local scheduling/IRQ constraint, not mutual exclusion with another CPU's ioctl/close. Its identity and selected scheduling branch in the eventual build still require binding. Acquiring a new slot lock from schedule under the runqueue lock creates an unreviewed order and IRQ/preemption requirement. A load followed by an event ref increment is insufficient because release may win between them.

Retained `f03_do_exit_supported_v2` reads current process monitoring pointer and passes it to child sync (:35621-35624); preemption was disabled and process threads lock is held in that path. `sync_child_event_body_result` (:19495) traverses event->group_leader and sibling list without local lifetime acquisition. Those locks cannot be treated as the scheduler or all-writer lock without evidence that every publication, stop and switch participates. `perf_stop_body_result` (:20327-20452) writes NULL and PP_NONE only for the current thread's process, after group/hardware operations; it is not a release of other processes' slots or existing readers. Process initialization sets the slot NULL (process_helpers.rs:7207), not a reference mechanism.

The retained combined C syscall.c:8282 copies inherited monitoring pointer into the fork child in the legacy branch of `#ifdef MCKERNEL_NATIVE_FORK_OWNED_TRANSACTION`; the alternate owned-transaction branch returns via a different path. Do not infer the selected branch or behavior of held owned-fork machinery. The retained Rust exit source and C terminate path also differ in surrounding thread locking, so exact selectors and source assembly matter. A child monitoring owner, if this inherited route is selected, needs its own pin and failed-fork rollback; no pointer copy itself acquires one.

First missing contract is one source-selected slot acquisition/replacement/retirement protocol that spans ioctl current and remote publication, scheduler reader in its actual runqueue/IRQ context, exit/group sync, stop, process teardown and every selected fork/inherit route. It must atomically protect loading the slot and obtaining a live reference, define old-slot replacement, drain all CPUs/readers before last event free, cover target process lifetime, and bind a deadlock-free order with runqueue, process-hash, thread, descriptor and group locks. The available process-hash read lock and per-CPU runqueue lock do not establish that common contract; no existing event reference API was identified. A shared slot lock plus refcounts could be designed only after these constraints and selected callers are independently bound. Close, group links, cross-thread counter owner and generic descriptor pins remain separate integration requirements. No actual Rust patch is offered because its correctness would depend on inventing the missing contract.
