# Perf group descriptor callback identity: source-only finding

Functional McKernel OS/apps and Rust/assembly migration only; no security testing. No Rust patch, compiler, test, Docker, native, guest, privilege, controller, cleanup or replay. The hash-bound inputs are in INPUT-HASHES.json; actual selected image, descriptor provenance and linkage remain unproved.

The retained perf entry binding (`f03_perf_entry_candidate.rs`:127-131) supplies five explicit functions `f03_perf_read_v1`, `f03_perf_ioctl_v1`, `f03_perf_mmap_v1`, `f03_perf_close_v1`, `f03_perf_fcntl_v1`. Its actual publisher (`syscall_policy.rs`:21240-21270) writes these callbacks and event data before inserting the mckfd under the process lock. This gives a recognizable callback tuple for a descriptor newly published through that exact binding. The selected C source has selector-conditional Rust aliases and alternate C fallback functions (`nonheld syscall.c`:20901-20907, 21363-21384), so a universal single callback-address identity is not established for all possible selected/mixed provenance. Rust fork can copy the callback bytes, but its event and descriptor ownership are separately unresolved. No distinct typed descriptor tag is present in Mckfd.

XPMEM descriptors use their own ioctl/close callbacks and store a process pointer in data (`xpmem_helpers.rs`:3470-3496); signalfd zeroes callbacks and stores a mask (`syscall_policy.rs`:1858-1890). These source facts make the exact perf callback tuple a plausible discriminator for those two producers in a completely bound image, but do not prove uniqueness across every enabled producer, legacy C descriptor, linker behavior or all accepted inherited descriptors. Checking all callbacks or only close must be reviewed against actual provider selection and legitimate group FD semantics; the original group helper accepts a matching perf member as well as a leader, so a new condition requiring self-leadership would change accepted behavior. Non-perf error behavior also needs an explicit oracle because the original helper reads data without a type check.

More immediate, group lookup (`syscall_policy.rs`:21065-21099) does not hold mckfd_lock and receives neither callback offsets nor lock/pin callbacks in its existing ABI. Close (:3625-3685) removes under lock and frees after unlock. Reading an additional callback through this same unpinned pointer is not a sound independent type check; checking under the lock and then invoking the unchanged helper after unlocking reintroduces FD/descriptor replacement and leader-free races. Holding the lock through the helper's lookup/link would require a new selected boundary, but still leaves group event/monitor/reader lifetime after unlock unresolved. Callback identity does not pin an event, authenticate a new tail allocation, or justify reinterpreting a non-perf payload.

A source-paired selected caller must supply an exact accepted provider/descriptor identity and under-lock non-resurrecting acquisition, preserve valid leader/member/clone/fallback cases, and define invalid-FD return. With no such existing API and no complete identity proof, a small type-check patch would not be independently sound or demonstrated behavior-preserving. No patch offered. This finding does not claim or fix concurrent close; descriptor/event/group and monitoring references remain open.
