  ## Three-day execution sequence

  These are scheduling targets. Advance when the preceding gate passes;
  unfinished prerequisite work retains priority throughout the 72 hours.

  ### Day 1 — Reconcile evidence and build a trustworthy execution path

  - Create a dated current-state ledger linking every tracker, all 130
    production gates, seven language gates, and all 273 application cases.
    Record implementation, review, build, runtime and acceptance separately.
    Preserve historical scores and reports.

  - Add an immutable correction manifest for the nine broken references. Check
    every declared input’s length/hash and every packet’s case coverage.
    Classify the 220 reviewer questions into already-specified answers,
    fixture defects, missing observations and missing OS capabilities.

  - Inventory all drafts; deeply review only the next eligible packet, with at
    most three active cases. Reject unconditional success, fabricated
    observations, incomplete parameter coverage and expectations derived from
    the tested implementation.

  - Implement the existing planned scripts/application-tests/run.py interface
    with --inputs, --case, --attempt, --profile and --mode. Reuse the
    catalog’s input, capability, packet and result schemas.

  - Implement concurrent stdout/stderr capture, raw wait-status handling,
    independent deadlines, QMP pause/resume recovery, exclusive attempt
    directories, and actual McKernel process/request provenance. Run identical
    payload bytes directly on the pinned Linux guest and through the unchanged
    launcher, resetting inputs between engines.

  - Verify the retained build/source bindings and replay all four original
    core modes, both control ABIs, and ordinary signal/futex regressions on
    the selected pair. Any production changes require new builds and bindings.

  Day 1 gate: trustworthy inventory, reviewed first packet, reproducible
  baseline, and tested execution infrastructure. Draft review can continue
  independently while infrastructure is repaired.

  Day 2 gate: evidence-backed execution release for a small supported subset.
  If ownership or infrastructure remains unresolved, continue that work and
  keep new application execution blocked.

  ### Day 3 — Accept supported applications and establish repeatability

  - Execute reviewed, dependency-ready cases in this order: startup and
    streams; allocation/VM and regular files; ordinary threads/futexes/local
    signals/time; unchanged utilities and deterministic numerical workloads.

  - Within each wave, follow existing queue order and skip only explicitly
    blocked dependencies, recording the reason. Extended loaders, successful
    fork, external signals and optional instructions require their own
    capability evidence.

  - After a short case first passes, run three additional repetitions in the
    same OS and one in a fresh guest with identical inputs.

  - Run the existing ten-cycle campaign only after its seven members pass:
    cat-file, wc-bytes, sha256sum, cp, numeric sort, gzip compression and
    decompression. Freeze guest batch membership beforehand and retain the
    300-second guest limit.

  - Spend remaining time on the earliest blocking functionality defect. Native
    shutdown/drain is the next major integration milestone; a complete
    shutdown implementation is a stretch outcome for this run.

  Day 3 deliverable: an exact accepted-case count, preserved failures and
  blocked dependencies, source-bound results, and a concrete next defect or
  integration task. If prerequisite gates consume the run, deliver their
  completed evidence and remaining blocker without claiming application
  acceptance.
