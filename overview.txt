How to read this number
------------------------------------------------------------

This is a functional-area estimate, not a strict line-count. The Rust build
foundation and first shared primitives are in place, but most high-risk kernel
subsystems remain C. A later tracking phase can add an automated line-count and
symbol ownership report.

Current completed Rust-owned behavior
------------------------------------------------------------

- Freestanding no_std Rust kernel crate exists under kernel/rust/.
- Rust can be linked into the x86_64 mckernel.img path.
- C fallback builds remain part of the migration contract.
- Rust exports C ABI replacements for the first rbtree, llist, and bitmap
  routines.
- Rust now owns bitmap_find_next_zero_area(), bitmap_find_free_region(),
  bitmap_allocate_region(), and bitmap_release_region() when
  ENABLE_RUST_KERNEL is on, while the C implementations remain available for
  fallback builds.
- Initial ABI/layout checks exist for shared structures.
- Primitive equivalence testing exists in kernel/rust/tests/run_equivalence.sh.

Known failing or blocked step:
- Full workload/runtime validation is not complete yet.
- V10 now reaches final user mode and `mcexec /bin/true` passes after the
  floating-point default-state restore fix.
- The current Rocky failure is the next smoke command, hostname execution. The
  target process reaches dynamic loader and libc setup, then dies with SIGSEGV
  after an instruction fetch at `RIP=0x1000`. Host-side `mcexec` exits with
  status 139 because it mirrors the target signal.
- The latest V10 matrix shows the failure is path-sensitive as well as
  VDSO-sensitive: relative `mcexec --disable-vdso hostname` passes, but
  absolute `mcexec --disable-vdso /usr/bin/hostname` still reaches `RIP=0x1000`.
  That points the next diagnostic pass at initial stack, argv/env layout,
  auxv/VDSO selection, and dynamic-loader return targets rather than treating
  VDSO as the only variable.
- The active diagnostic pass resets bounded `mcexec_v10:` counters per process
  and records syscall returns, offload returns, VDSO/auxv setup, signal
  delivery/default termination, fatal page-fault registers, initial stack
  markers, and byte/ascii dumps for user-range pointers found in the fatal
  register/stack state. This should show whether `0x1000` came from a bad
  signal handler, VDSO/auxv value, argv/env stack setup, dynamic loader state,
  or syscall return path.
- The Rocky validation script now wraps each V10 smoke command in a timeout so
  future runs stop at the first failing command and print command output plus
  recent McKernel kmsg.
- The first timeout wrapper had a shell-status capture bug: after
  `mcexec-true` failed or timed out, it printed status `0` and continued to
  `mcexec-hostname`. The wrapper now preserves the actual `timeout` status and
  stops at the first failing smoke command.
- V10 smoke now runs `mcexec` with `--debug-mcexec`, can optionally run under
  `strace` with `--trace-smoke`, and dumps Linux process state, Linux dmesg,
  recent McKernel kmsg, and `mcexec_v10:` handoff markers on failure.
- The smoke watchdog default is now 8 seconds. The script uses an explicit
  `setsid`-based watchdog instead of relying on GNU `timeout`, because a stuck
  kernel ioctl can prevent `timeout` from returning cleanly.
- After a V10 hang, the next boot attempt can fail early while destroying the
  previous `/dev/mcos0` OS instance. The validation script now runs
  `mcstop+release.sh -k` before boot-smoke and during watchdog cleanup so stale
  `mcexec` holders are killed before a fresh boot is attempted.
- The V10 watchdog now tracks the direct smoke-command PID instead of a
  `setsid` process group and prints the watched PID immediately. Failure
  diagnostics that can themselves block are bounded with short timeouts.
- There is no current Rocky VM build or module-load blocker after V8.
- The V8 trampoline warning remained after reducing the x86_64 private
  trampoline allocation to one low-DMA page. The persistent GRUB `memmap`
  reservation experiment was unsafe on Rocky/VirtualBox, so the safe default is
  to continue V9 with the Linux-trampoline fallback and no persistent boot-arg
  changes.
- V9 boot-only passed with the Linux-trampoline fallback. The boot log still
  reported `Trampoline area: 0x0` and `error: allocating fp_regs pages`, so V10
  should be treated as the next runtime boundary rather than assuming workloads
  are already validated.
- WSL remains blocked for real boot/runtime smoke testing by host module and
  kernel development tree limitations.
- ihk-smp-x86_64 compatibility against Linux 6.6 needs more work before WSL can
  be considered a runtime validation host.

Recommended verification style
------------------------------------------------------------

Run the ladder from plan.txt in order:

V0: Documentation integrity
V1: Source inventory
V2: Rust object only
V3: Rust primitive equivalence
V4: Rust-enabled kernel image
V5: C fallback kernel image
V6: User-space tools
V7: Host modules compile
V8: Module load only
V9: McKernel boot only
V10: Minimal user workloads
V11: Focused regression tests
V12: Phase-specific stress

Stop on the first failing step. Record the failing command, environment, and
error summary in kernel.log before making more changes.

Next migration target
------------------------------------------------------------

Recommended next code phase:
- Phase 1: harden the Rust build foundation and make the Rust/C fallback checks
  easier to run repeatedly.

Recommended next risky code phase after that:
- Phase 2: expand ABI/layout coverage before porting memory management.

Reason:
- Memory, process, and syscall ports depend on exact layout stability. Expanding
  layout checks first reduces the chance of subtle C/Rust ABI drift.
